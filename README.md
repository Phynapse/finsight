# FinSight

**Financial intelligence with deterministic analytics and grounded AI explanations.**

FinSight is a portfolio project demonstrating responsible application of language models to financial data. It answers business questions in natural language against a controlled synthetic dataset. Every number is computed deterministically in Python/Pandas. The AI interprets the question and explains validated evidence — it never calculates.

> **Synthetic data only. Not financial advice. Not an accounting system.**

---

## Core Principle

```
USER QUESTION
    │
    ▼
Question Interpreter   ← rule-based (Phase 1); LLM-upgradeable (Phase 2)
    │  structured interpretation
    ▼
Analysis Planner       ← deterministic: only catalogued types are accepted
    │  validated AnalysisPlan
    ▼
Deterministic Analytics Engine   ← Python / Pandas — all arithmetic lives here
    │  metrics, breakdown, series
    ▼
Evidence Package       ← every fact carries source_dataset + formula
    │
    ▼
Explanation Generator  ← rule-based templates (Phase 1); LLM-upgradeable (Phase 2)
    │  grounds each sentence in an evidence item ID
    ▼
Structured Answer      ← answer + interpretation + evidence + caveats
```

The LLM does **not** calculate financial values. It interprets questions and explains results. This boundary is enforced by design: the analytics layer never passes raw questions to the model; the explanation layer never receives raw data.

## Quick Start

```bash
# 1. Clone and enter
git clone <repo>
cd FinSight

# 2. Backend
python -m pip install -r backend/requirements.txt
```

## Dataset

Four synthetic CSV files bundled in `data/`. Generated by `scripts/generate_data.py` with `SEED=20260101`.

| File | Rows | Coverage |
|---|---|---|
| `financial_data.csv` | 8 | FY2023–FY2024 quarterly income statement + cash flow |
| `transactions.csv` | 233 | FY2024 operating expense ledger |
| `budgets.csv` | 148 | FY2024 monthly budget vs actual by department/category |
| `vendors.csv` | 17 | Vendor master with contract metadata |

**Sign convention:** `amount` is always positive; `transaction_type=expense` adds to spend; `transaction_type=credit` subtracts. Net spend = Σ expense − Σ credit.

**Assumptions baked into the generator:**
- `OPENING_CASH = 6,200,000.00`
- `EFFECTIVE_TAX_RATE = 0.22`
- `CAPEX_RATE_OF_REVENUE = 0.025`
- `WORKING_CAPITAL_RATE_OF_REVENUE_CHANGE = 0.18`

All 11 cross-dataset integrity checks pass at startup. Four quarterly ledger-to-income-statement tie-outs confirm the datasets are internally consistent.

## Supported Analysis Types

| ID | Description | Key Metrics |
|---|---|---|
| `metric_snapshot` | Single metric for a period | Any catalogued metric |
| `revenue_performance` | Revenue, COGS, gross profit, gross margin | `revenue`, `gross_margin_pct` |
| `expense_analysis` | Cash vs non-cash split, dimension attribution | `total_expense`, `operating_expenses` |
| `expense_variance` | Period-over-period movement, contribution table | `operating_expenses` |
| `profitability` | Full P&L walk with margin analysis | `operating_margin_pct`, `gross_margin_pct` |
| `budget_variance` | Actual vs approved budget | `budget_variance`, `budget_utilisation_pct` |
| `vendor_spend` | Spend by supplier with concentration | `vendor_concentration_pct` |
| `trend` | Ordered time series, first-to-last growth | Any statement or ledger metric |

## API

```
GET  /api/v1/health                         Liveness + readiness
GET  /api/v1/capabilities                   Metric catalog, analysis types, periods
GET  /api/v1/datasets                       List bundled datasets
GET  /api/v1/datasets/{id}/summary          Metadata + integrity checks
POST /api/v1/analysis                       Execute a deterministic analysis plan
GET  /api/v1/analysis/{id}                  Retrieve a previous result
GET  /api/v1/analysis/{id}/evidence         Evidence package for a result
POST /api/v1/questions                      Full pipeline: question → answer
```

Interactive docs: `http://localhost:8000/docs`

### Example: POST /api/v1/questions

```json
{
  "question": "Why did operating expenses increase in 2024-Q4?"
}
```

Response includes:

- `status`: `answered` | `unsupported` | `failed`
- `interpretation`: matched metric, analysis type, period, confidence
- `plan`: the validated `AnalysisPlan` that was executed
- `analyses`: list of `AnalysisResult` with metrics, breakdown, series, methodology
- `evidence`: every fact with `source_dataset` and `calculation`
- `explanation`: summary, findings, grounded evidence IDs
- `caveats`: what the data does and does not establish
- `llm_enabled`: whether a live LLM was used

## Configuration

Copy `.env.example` to `.env`. All values have safe defaults; the API runs without any configuration.

| Variable | Default | Description |
|---|---|---|
| `APP_ENV` | `development` | Environment name |
| `DATA_DIR` | `data` | Path to CSV files |
| `API_PREFIX` | `/api/v1` | URL prefix |
| `CORS_ORIGINS` | `http://localhost:5173,...` | Allowed browser origins |
| `MAX_REQUEST_BYTES` | `16384` | Body size cap |
| `LLM_PROVIDER` | `disabled` | `openai`, `anthropic`, `ollama`, or `disabled` |
| `LLM_API_KEY` | _(none)_ | API key — never logged |
| `LLM_BASE_URL` | _(none)_ | Override endpoint (Ollama, Azure, etc.) |
| `LLM_MODEL` | _(none)_ | Model name |
| `LLM_TIMEOUT_SECONDS` | `20` | Per-request timeout |

When `LLM_PROVIDER` is `disabled` or no API key is set, the deterministic rule-based implementations run instead. The API still answers questions; explanations are assembled by template rather than generated by a model.

## Architecture Decisions

See `docs/ARCHITECTURE.md` for full detail. Summary:

1. **Deterministic analytics first, language model second.** Financial arithmetic in Python/Pandas is reproducible, testable, and auditable. A language model explaining validated evidence is far more reliable than a language model producing or modifying financial values.

2. **The AnalysisPlan is a closed vocabulary.** The interpreter can only produce plans whose `analysis_type` and `metric` are in the catalog. Arbitrary operations are impossible by construction.

3. **Every fact carries provenance.** `EvidenceItem` has `source_dataset`, `source_fields`, and `calculation`. The explanation generator receives only the evidence package — it cannot access the raw DataFrames.

4. **LLM output is validated before use.** Phase 1 uses rule-based implementations. Phase 2 LLM output will be parsed into `Interpretation` and `ExplanationDraft` Pydantic models; a failure to parse returns a structured error, not a hallucinated answer.

5. **No hosted infrastructure.** In-memory TTL store, bundled CSV files, single Python process, static frontend. Suitable for a portfolio demo and easy to inspect.

## Known Limitations

- Phase 1 uses rule-based interpretation. A question like "What were the largest expense categories?" returns `unsupported` because no catalogued metric has a "categories" alias. Phase 2 replaces this with an LLM that produces validated `Interpretation` objects.
- The ledger covers FY2024 only. Budget variance and vendor spend analyses on 2023 periods have no actual-spend data.
- The in-memory store is cleared on restart. Analysis IDs are ephemeral.
- Concentration metrics use the `vendor_id` foreign key (one-to-one with vendor spend); a vendor with multiple IDs across cost centres appears split.
- The rule-based explanation generator produces correct but formulaic narratives. A configured LLM produces more natural prose.
